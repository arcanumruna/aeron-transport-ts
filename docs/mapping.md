# Source and test mapping

One row per ported file (spec §5, §8.1). `aeron:` paths are relative to the Aeron `1.53.3` checkout and `agrona:`
paths to the Agrona `2.6.1` checkout (`npm run fetch:refs`). `npm run check:mapping` checks the **Tests** and
**Skipped tests** tables against both sides: every Java test name has a TS test of the same name and the reverse,
the counts are current, and every `it.skip` is listed with its reason.

## Golden wire vectors

`test/golden/goldenFrames.test.ts` is not a port of a Java test, so it has no row in **Tests**. It checks the flyweights
and `FrameDescriptor` alignment against bytes that two real Aeron 1.53.3 **C** drivers exchanged (plan T13):

| File | What |
|---|---|
| `scripts/capture-golden.mjs` | Runs `aeronmd` x2, `basic_publisher`/`streaming_publisher` and `basic_subscriber` in five scenarios (`basic`, `fragmented`, `pad`, `loss`, `setup-elicit`) through a loopback UDP relay that records every datagram, drops one chosen DATA frame in `loss`, and decodes each frame with an independent `DataView` decoder (offsets from `aeron_udp_protocol.h`). It keeps the first 12 datagrams of each frame class per scenario (the RTT measurement alone produces thousands) and always keeps PAD, NAK and SETUP. |
| `test/golden/frames.json` | The committed capture: 263 datagrams. Frame kinds: SETUP, SM plain, SM with `SEND_SETUP` (0x80), SM with the end-of-stream flag (0x40), DATA unfragmented (0xc0), BEGIN (0x80) / MIDDLE (0x00) / END (0x40) fragments of a 3500 byte message at MTU 1408, PAD at term end (a PAD header follows the last data frame in the same datagram), heartbeat (0xc0, frame length 0), EOS heartbeat (0xe0), NAK, the retransmitted DATA, RTTM request and reply. |
| `test/golden/goldenFrames.test.ts` | Per datagram: walks the frames with `FrameDescriptor.FRAME_ALIGNMENT`, decodes with the flyweights and compares to the recorded fields, re-encodes into a fresh zeroed buffer and compares the bytes. A coverage block asserts every type and flag above against the C header literals (and the per-frame `flagNames` the capture script derives from its own copy of the C flag constants); a constants test pins every TS `HDR_TYPE_*` and flag to those literals. Needs no C driver. |

To re-run the capture, see the README ("Golden wire vectors").

Not in these flows, so covered by their flyweight tests only: ERR, RSP_SETUP, RES, ATS frames.

Facts the capture showed about the 1.53.3 C driver, which the flyweight tests did not pin down:

- A heartbeat is a bare 32 byte DATA header whose `frameLength` field is `0`, not `32` (`DataHeaderFlyweight.isHeartbeat`).
- A PAD frame is sent as its 32 byte header only; its `frameLength` covers the whole pad to the end of the term.
- The C receiver's RTTM **request** carries `REPLY_FLAG` (0x80, "please reply"); the sender's **reply** has the flag clear.
- The C sender puts the PAD header in the same datagram as the preceding data frame(s).

Fields the stock C samples never vary, so the golden vectors only show one value and the flyweight unit tests alone cover the rest: `reservedValue` (always 0), RTTM `receptionDelta` (always 0), `version` (always 0) and a negative `frameLength`. Also not varied: the pinned session id, stream id and term ids (one value each per capture).

The capture pins `sessionId` to a negative int (0x87654321), `streamId` to 0x12345678 and starts the publication one term after the initial term, so SETUP has `activeTermId` = `initialTermId` + 1. `frames.json` records, per scenario, the NAKs the deliberate drop did not cause (`unintendedNaks`: the relay can drop datagrams under a burst); the NAK checks are scoped to the deliberate drop.

Flyweight disagreements with the real bytes: none found. (No `it.skip` was needed.)

## Iteration counts

The Java tests run their random round trips for 1,000,000 (`AsciiEncodingTest`) and 10,000,000 (`MutableDirectBufferTests`) iterations. Both loops run `count / ITERATIONS_SCALE` iterations, where `test/support/Iterations.ts` has `ITERATIONS_SCALE = process.env.AERON_TS_FULL_ITERATIONS ? 1 : 100`. CI sets `AERON_TS_FULL_ITERATIONS=1` on the Node 24 job only.

So that the full-size round trips fit in `ROUND_TRIP_TIMEOUT_MS` (180 s), `putLongAsciiRoundTrip`, `putNaturalLongAsciiRoundTrip` and `parseLongAsciiRoundTrip` set `Error.stackTraceLimit = 0` during the loop (restored in `finally`) and take the overflow (throwing) branch on one iteration in eight only: on `i % 8 === 0` the value is the full-range `randomJavaLong(i >> 3)`, on the others `randomJavaLong(i)` folded into the safe range with `BigInt.asIntN(53, ...)` (`asUintN(53, ...)` for the natural one) when outside it. The overflow assertion is unchanged.

## Deviations

The deviations of this port that touch these files (the full list is spec section 6):

| # | Deviation |
|---|---|
| D5 | Every Java `long` is a `number` in +/-(2^53 - 1). A result or stored value outside that range throws `RangeError` (`LongOverflowError` when it is a parsed or stored long, carrying the exact value) and writes nothing; it never wraps. It covers get / put / getAndAdd / add / compareAndSet of longs, `putLongAscii`, `parseLongAscii`, `parseSize` / `parseDuration` and the `BitUtil` long helpers. The one exception is a saturating function: Java's `parseDuration` saturates at `Long.MAX_VALUE`, here at 2^53 - 1. |
| D5 (commands) | The `long` client, correlation, registration and position fields of the command flyweights are `number`s in +/-(2^53 - 1) (spec 5.2): they are allocated from `nextCorrelationId` and counted, so 2^53 needs 2^53 commands. `PublicationErrorFrameFlyweight.receiverId` and `groupTag` are the exception: Java's receiver id is a random 64-bit value (UUID bits XOR, incremented), so they are `bigint` as in `ErrorFlyweight`. The one flags word (`RemovePublicationFlyweight`) is read and written as its low `int` (bit 0), so a peer's word outside the range never throws and the high half stays byte-identical. |
| D4, D15 (CnC) | `CncFileDescriptor` lays the CnC out in a `SharedArrayBuffer`; the file, `MappedByteBuffer` and file name members are not ported (see **Not ported**). |
| `static length` | `RemoveMessageFlyweight.length()` and `RemovePublicationFlyweight.length()` are static methods named `length`, which hide the `Function.length` of the class (TypeScript accepts it with `override`). A subclass has its own `length` data property, which hides an inherited static method of that name, so `RemoveSubscriptionFlyweight` declares `static override length()` itself (Java inherits it). |
| D9 | No `java.nio.ByteBuffer` and no raw addresses: buffers wrap an `ArrayBuffer` or a `Uint8Array`. `verifyAlignment` checks `byteOffset + addressOffset` of the window in its `ArrayBuffer`. |
| D10 (collections) | `java.util` (`Iterator`, `Map.Entry`, `AbstractCollection`, `AbstractSet`, `NoSuchElementException`, `Objects.equals` / `hashCode`, `Arrays.copyOf`, `Float.toString`) lives in `src/agrona/jdkUtil.ts`, next to `jdk.ts`. A key or value is hashed and compared through a `hashCode()` / `equals()` protocol (`HashCoded`), as `String`, `Integer` / `Double`, `Boolean`, `Long` for the primitives, and by identity (`WeakMap` hash, `===`) for any other object. `jdkUtil.ts` is a second JDK stand-in file beside `jdk.ts`; `String.hashCode` is computed on every call (a JS string caches none); a `number` key is hashed as an `Integer` if it is an int32 and as a `Double` otherwise. |
| D5 (collections) | `Long2*` maps hold `long` keys (and `Long2LongHashMap` values) as `number` in `Float64Array`s. A key or value that a mutator would store outside +/-(2^53 - 1) throws `RangeError` and changes nothing; lookups (`get`, `containsKey`, `remove`) never throw, an unsafe key is just not found. `Hashing.hashLong` is exact over the whole safe range (a `bigint` reference test), `Hashing.compoundKey` throws `LongOverflowError`. The `int` maps do not check: every keyed method normalises the key with `key | 0`, Java's `(int)` cast at the call site, so a key past 32 bits is the same wrapped key in `put`, `get`, `containsKey` and `remove`. A `-0` key or value of a `Long*` map is stored as 0. |
| D10 | The JDK exception classes live in `src/agrona/jdk.ts`, not in `exceptions.ts`; the stand-ins added by the agents and counters (`Thread`, `Charset`, `AutoCloseable`, `InterruptedException`, ...) are in `src/agrona/jdkLang.ts`. |
| D11 | Agents run on the event loop. `AgentRunner.run()` returns after `onStart`; each duty cycle is a task on `setImmediate`, or on a timer for a park. Idle strategies do not block: `idle()` returns the wait in nanoseconds (spin and yield 0, park the period; the timer is `ceil(ns / 1e6)` ms, at least 1). `Thread.currentThread()` is a logical thread with an interrupt flag (the main thread, or the runner's during its cycles). `close()` of a runner from outside the agent ends it at once. |

| D12 | Log buffer raw tails are `bigint` (a term id is any `int`, so the packed 64-bit value cannot be a `number`): `LogBufferDescriptor.packTail`, `rawTail`, `rawTailVolatile`, `casRawTail`, `termId(rawTail)`, `termOffset(rawTail[, termLength])`; the slot is two little-endian int halves, `rawTailTermId`, `rawTailTermOffset` and `initialiseTailWithTermId` use the halves without a `bigint`.
